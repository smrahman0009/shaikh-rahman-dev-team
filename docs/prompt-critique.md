# Independent critique of the original request

The business objective is coherent: a CEO supplies informal requirements; a CTO coordinates selectively activated specialists and independent review, producing evidence-backed deliverables. The original is unusually explicit about scope, review, permissions, and honest limitations. Its main implementation risk is treating instructions as runtime guarantees.

This assessment was written from the original attachment before reading other agents' conclusions. It evaluates the specification, not the finished implementation. The unchanged source is [prompt-original.md](prompt-original.md).

| Finding | Impact | Required refinement | Verification |
| --- | --- | --- | --- |
| “Production-minded” and “minimal supervision” have no operational threshold. | Delivery can look complete without repeatable recovery or acceptance. | Define observable acceptance scenarios; report human interventions and unknown metrics. Avoid claiming production certification. | Run the scenario matrix and report evidence and limitations. |
| Native agent settings, instructions, and durable state have different authority. | A role file may be mistaken for a scheduler, security boundary, or billing cap. | Label each control as platform-enforced, code-enforced, or instruction-only. | Inspect control paths and attempt prohibited state transitions. |
| A separate critic role does not itself establish independence. | Producer rationale can anchor a supposedly independent assessment. | Spawn a fresh context with original requirements, criteria, artifacts, and evidence; capture its initial assessment before revealing rationale. | Demonstrate a real separate-context review and distinguish it from a simulated ledger test. |
| “Every substantive stage” needs a bounded meaning. | Either trivial work becomes expensive or stages evade review. | Require critique for requirements, consequential design, substantive implementation, and final claims. Permit one brief critic pass over combined small-task artifacts. | Show both a defect-bearing task and a trivial task with proportional activation. |
| Budgets mix observable counters with unavailable monetary usage. | An estimated cost may become a false hard spending guarantee. | Enforce measurable limits at local operations; label external execution and billing limits explicitly. Unknown cost stays unknown. | Exhaust a configured counter and prove further controlled progression is blocked. |
| Retry, revision, experiment, and research loops lack counting semantics. | A loop can reset its own budget or retry forever after restart. | Persist counters; default to two revision rounds per stage; define blocked outcomes and reset authority. | Restart near a limit and confirm it remains exhausted. |
| Cancellation and recovery could imply an unattended service. | Saved “running” tasks may be accepted after interruption, or cancellation may be assumed to kill tools. | Treat the initial system as an interactive Codex workflow plus durable ledger. Reconcile source and task state before resume; describe process termination separately. | Simulate interruption and repository drift; require revalidation before delivery. |
| Change invalidation and stale-result detection need explicit provenance. | A late task can approve the wrong requirement or artifact version. | Associate tasks, reviews, and verification with requirement/artifact revisions and invalidate affected downstream records. | Change a requirement during execution and reject the old result. |
| Shared learning creates a cross-project disclosure risk. | Local decisions or secrets may become universal guidance. | Scope records, require review before promotion, and record applicability, evidence, contradiction, revision, retirement, and deduplication. | Reject unreviewed promotion; demonstrate project-scoped retrieval and contradictory-lesson handling. |
| Model discovery is capability-dependent. | A static model alias or invented price can masquerade as live discovery. | Use the current platform's exposed availability where possible; inherit a supported model when discovery is unavailable. Record the limitation and never invent prices. | Inspect the recorded discovery source or explicit fallback. |
| Framework breadth could consume effort meant for practical delivery. | A new API orchestration stack, auto-installer, or unrelated app changes inflate cost and risk. | Keep reusable files isolated; use native skills/roles and a standard-library ledger where sufficient. No automatic runtime installation or assumed API credentials. | Inspect the diff, setup documentation, and dependency footprint. |

## Acceptance interpretation

Successful delivery means the supported entry point, role definitions, durable workflow controls, templates, examples, and validations exist and can be inspected. It does not mean the system guarantees correctness, measures unavailable token billing, automatically trains models, runs forever unattended, or overrides host permissions. A human or agent can still bypass a local CLI by editing its storage; the ledger is a workflow gate, not an adversarial security boundary.

The revised [implementation brief](implementation-brief.md) makes those boundaries explicit while retaining the business requirements. Any unsupported requirement must appear as a named limitation with a practical operational fallback, rather than disappear from the delivery report.
